# Frontend CI APK Build Performance — Analysis & Plan

## Problem

`Frontend Build` (`.github/workflows/frontend-build.yml`) takes ~20-25 minutes per run, vs. the backend deploy workflow which finishes in a few minutes. Every push to `main` touching `frontend/**` triggers a full signed release APK build + GitHub Release, so this cost is paid on essentially every frontend commit.

## Where the time actually goes

Pulled step-level timings for the three most recent runs via `gh api .../actions/runs/<id>/jobs`:

| Step | Run 1 (20m03s total) | Run 2 (22m04s total) | Run 3 (24m07s total) |
|---|---|---|---|
| checkout + setup-node + setup-java | ~5s | ~5s | ~5s |
| Install dependencies (`npm ci`) | 15s | 19s | 20s |
| Lint | 3s | 3s | 3s |
| Prebuild native Android project | 3s | 3s | 4s |
| **Build release APK (`gradlew assembleRelease`)** | **19m17s** | **21m11s** | **23m19s** |
| Create GitHub Release | 9s | 9s | 9s |

The Gradle release build is >95% of the total in every run — everything else is noise. So "make the workflow faster" is really "make `assembleRelease` faster," not a general audit of the whole pipeline.

## Root causes

1. **No Gradle caching between CI runs at all.** The workflow has zero cache step for `~/.gradle` or the Gradle wrapper distribution. Every run re-downloads every Maven dependency (AndroidX, Kotlin stdlib, the Android Gradle Plugin, per-native-module dependencies) from scratch, and recompiles every Kotlin/Java source in React Native core and every native module (`react-native-reanimated`, `react-native-worklets`, `react-native-gesture-handler`, google-signin, etc.) with a cold build cache, then runs R8/dexing from scratch. This is the dominant cost.
2. **The release APK is built for 4 ABIs**, per `android/gradle.properties` (Expo's default template, not something we set explicitly): `armeabi-v7a,arm64-v8a,x86,x86_64`. `x86`/`x86_64` are emulator-only architectures — no real Android phone uses them. Building and packaging native libraries for them is pure overhead for an APK meant for sideloading onto real devices.
3. R8 minification (`minifyEnabled enableMinifyInReleaseBuilds`, default `true`) is genuinely part of the cost of a real release build. This is expected and not something to cut — noted for completeness, not proposed as a change.

## Proposed changes, ranked by impact/effort

### 1. Turn on Gradle caching across runs (highest impact, lowest risk)

Add the official [`gradle/actions/setup-gradle@v4`](https://github.com/gradle/actions) action after the prebuild step (it needs `android/` — which is gitignored and generated by `expo prebuild` — to exist first) and before the build step:

```yaml
- name: Prebuild native Android project
  run: npx expo prebuild --platform android

- uses: gradle/actions/setup-gradle@v4

- name: Decode release keystore
  ...

- name: Build release APK
  working-directory: frontend/android
  run: |
    ./gradlew assembleRelease --no-daemon --build-cache \
      -PRELEASE_STORE_FILE=release.keystore \
      ...
```

This caches the Gradle Wrapper distribution and `~/.gradle/caches` (downloaded dependencies) between workflow runs, and — combined with the `--build-cache` flag — backs Gradle's build cache with the GitHub Actions cache backend so compiled outputs (Kotlin/Java compilation, R8/dexing) are reused whenever their inputs (source, dependency versions) haven't changed. Since `node_modules` native sources rarely change between commits, most commits should become near-total cache hits after the first (cold) run following this change.

### 2. Only build ABIs that ship to real devices

Add `-PreactNativeArchitectures=arm64-v8a,armeabi-v7a` to the `./gradlew assembleRelease` invocation, dropping `x86`/`x86_64`. This property is already read by the generated `gradle.properties` (the comment there explicitly documents CLI override via `-P`) — no plugin or prebuild change needed.

**Tradeoff:** the CI-built release APK will no longer install on x86/x86_64 emulators. That's fine for an APK meant for sideloading onto real phones; local dev builds via `npm run android` are unaffected and keep all 4 ABIs for emulator use.

### 3. (Optional) Bigger GitHub-hosted runner

If #1 and #2 together still leave the build slower than desired, a paid `ubuntu-latest-4-core` (or 8-core) runner gives more CPU for Gradle's parallel task execution and R8. Worth revisiting only after caching is in and measured — caching should provide the bulk of the win for free, so paying for more cores first would be premature.

### 4. (Optional, changes behavior — not just speed) Gate full release builds

Right now every push to `main` under `frontend/**` produces a signed APK + GitHub Release. If that's more frequent than actually needed, the signing/build/release steps could be restricted to `workflow_dispatch` or version tags, with a cheap lint-only job left on every push. This is a scope/cadence decision, not a build-speed fix, so it's listed as optional rather than recommended — only pursue it if the team decides not every commit needs a distributable artifact.

## Expected impact

Hard to give an exact number without measuring, since it depends on cache hit rate, but the shape to expect: the **first** run after adding caching will not be faster (cold cache, same ~20+ min) — the payoff shows from the **second** run onward, where unchanged-dependency builds commonly drop from ~20 min to single-digit minutes (mostly JS bundling, final dexing/packaging, and keystore/signing work that can't be cached away). ABI trimming (#2) saves on top of that regardless of cache state, since it's less native packaging work every single run.

## Verification after landing

- Land #1 and #2 together.
- Watch the next 2-3 runs' `Build release APK` step duration (`gh run view <id> --json jobs`, or the Actions UI) — expect run N+1 to still be slow (cache cold), run N+2 onward to show the drop.
- If the drop isn't there, check the `setup-gradle` action's cache-hit summary in the job log before reaching for #3.

## Not changed

- **R8/minification** — stays on. It's core to what makes this a real release build (smaller, obfuscated APK); trading that away for CI speed isn't a good deal for the artifact that becomes "the release."
- **npm ci / lint / prebuild / release-upload steps** — already <30s combined, not worth further optimization.
